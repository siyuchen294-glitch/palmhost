# 02 · 环境与选型

这一节记录**为什么是这么选**，以及被否掉的方案 —— 选型理由比结论更有复用价值。

## 为什么 Termux + proot，而不是 root / 刷机

| 方案 | 结论 |
| --- | --- |
| Root 后直接跑 | 需要解锁/刷机，vivo 机型门槛高，且会破坏保修与安全模型 |
| Docker / LXC | Android 上无内核特性支持，不可行 |
| **proot-distro** | ✅ 用户态模拟，**不需要 root**，能跑完整 Ubuntu 24.04 与 aarch64 二进制 |

代价：proot 有系统调用拦截开销，但对「聊天 + 调 API」这种低 I/O 负载完全够用。

## 为什么 NapCat 而不是官方机器人框架

官方 QQ 机器人（Bot 开放平台）走的是「官方 Bot 号」，功能受限、需要审核、**不能用自己的私人 QQ 号**。

我们的目标恰恰是「**让一个个人 QQ 号拥有 AI**」，因此必须走协议侧框架：

| 框架 | 评价 |
| --- | --- |
| **NapCat** | ✅ 基于 NTQQ 注入，维护活跃、OneBot 11 兼容、有 WebUI |
| SnowLuma | 也评估过（同为协议侧），文档与生态相对薄，最终选 NapCat |
| go-cqhttp 等老框架 | 已不适配新版 NTQQ 协议 |

> ⚠️ NapCat 是**注入式**方案：QQ 自动更新后注入点会失效。必须**锁版本**（本项目锁 3.2.32）并关闭自动更新。

## 为什么要有 xvfb

Linux QQ 是带 GUI 的程序，在没有显示设备的容器里起不来。用 `xvfb-run` 起一块虚拟屏：

```bash
xvfb-run -a -s "-screen 0 720x1280x24" /opt/QQ/qq --no-sandbox
```

`--no-sandbox` 在容器里是必需的，否则 Chromium 内核的沙箱会直接拒绝启动。

## 免扫码登录：`-q` 参数

第一次扫码登录后，QQ 会把登录态落到本地。之后启动带 `-q <QQ号>` 就能跳过二维码：

```bash
/opt/QQ/qq --no-sandbox -q <BOT_QQ>
```

**这是整套方案能「无人值守」的前提**。没有它，每次掉线都要人拿手机扫码。

## 为什么放弃 LangBot，改自写 bot

项目初期确实评估并实际部署过 LangBot（生产级可视化机器人平台，支持 DeepSeek/Dify/GPT 等）。

**放弃原因**：

| LangBot 优点 | 但对我们不成立 |
| --- | --- |
| 可视化配置、多平台 | 我们只有一个 QQ 号、一个平台 |
| 插件生态 | 我们需要的能力（群聊状态机、表情包池、逐人记忆）都是**深度定制逻辑**，插件表达不了 |
| 开箱即用 | 它跑起来占内存，手机只有 12G 且要和 QQ 抢 |

**自写 bot 的收益**：单文件 45KB 的 `bot.py`，所有逻辑可见可改，内存占用小，出问题直接看源码。

> LangBot 的部署文件仍保留在本地备份目录，作为「可视化看数据」的辅助工具。

## 为什么是 DeepSeek

- OpenAI 兼容格式：换模型只改 `DS_URL / DS_MODEL / DS_KEY` 三个变量
- `deepseek-chat` 中文对话质量好、价格低，适合高频闲聊
- 实测 `[llm Xms]` 日志里的往返延迟 **1–2 秒**，在聊天场景可接受

## 为什么 TTS 用 edge-tts

见 [07-tts.md](07-tts.md)：本地大模型在 ARM 上不可实时，edge-tts 是唯一「免费 + 快 + 中文音色多」的选项。
