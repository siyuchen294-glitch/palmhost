# 07 · 语音与 TTS：ARM 上的真实边界

结论先行：**手机端不要指望本地大模型 TTS，老老实实用 edge-tts。**

## 实测对比

| 方案 | 部署位置 | 单句耗时 | 结论 |
| --- | --- | --- | --- |
| **edge-tts** | 在线（微软） | **1–2s** | ✅ 采用 |
| ChatTTS | 手机本地（ARM） | **86s/句** | ❌ 不可实时，已装未启用 |
| GPT-SoVITS | 手机本地 | 更慢 | ❌ 已装未启用 |
| Kokoro | 手机本地 | 可出音但音质一般 | ⚠️ 作为降级备用 |
| 云端声音克隆 | 付费 API | 取决于厂商 | 未做 |

## 为什么本地 TTS 在手机上不现实

三个叠加因素：

1. **ARM CPU 无推理加速**：x86 + GPU 上几秒的任务，在手机 CPU 上放大 20–50 倍
2. **内存不够**：ChatTTS 模型 2.3G+，还要和 QQ、Ubuntu 容器抢 12G 内存
3. **发热降频**：连续合成会触发温控，越跑越慢

想过用 `torch` 的 aarch64 wheel 优化，结果卡在安装环节（见 [08-踩坑](08-pitfalls.md) 的 pip OOM 记录）。

**所以语音链路定成**：`文本 → edge-tts → mp3 → NapCat 发语音消息`。

## 语音模式

| 模式 | 行为 |
| --- | --- |
| `off` | 从不发语音，纯文字 |
| `mirror` | 对方发语音我才回语音（默认） |
| `always` | 一律发语音 |

`mirror` 是默认值，因为它最符合社交直觉：**对方用语音说明他方便听，我用语音才不会打扰**。

## 降级链路

语音会失败，必须有多级降级，否则一条语音失败就把整条回复吞了：

```
edge-tts 合成
   ├─ 成功 → 发语音
   ├─ 失败 → Kokoro 本地合成
   │             ├─ 成功 → 发语音
   │             └─ 失败 → ▼
   └───────────────────→ 纯文字回复（永不因语音失败而丢消息）
```

**原则：语音是锦上添花，不能成为消息送达的单点依赖。**

## 缓存

合成结果落在 `data/tts/`，同一文本短期内重复合成直接复用。

上线一段时间后记得清：`df -h /data` 看剩余空间，TTS 缓存 + 表情包池是主要增长源。
